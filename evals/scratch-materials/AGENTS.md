# AGENTS.md

Norms recorded here are grounded in real incidents hit while building this repo — not abstract best practices. Each entry cites the specific finding(s) that produced it.

## Reusing an external system "unmodified" surfaces its real constraints only by building against it, not by reading its docs or intent.md's constraints section first

This repo has hit four real incidents from the same root cause, all while reusing `tokenized-deposit-settlement` unmodified per intent-001.md's constraint:

1. **Signing-key model** (Phase 4, `project-findings-and-working-notes.md`): spec-001.md assumed the cash leg was authorized by "the bank's own operator authority." Reading the bank's actual `transferFlow.ts` showed an ordinary transfer is authorized by the client's own bank-custodied key — bank-ops never signs one. Found only by reading the real transfer code while building against it, not by anything in intent.md or spec.md's own drafting.
2. **Ledger-ownership gap** (Phase 4, `project-findings-and-working-notes.md`): composing the cash-leg transaction externally to the bank's own `/transfers` endpoint (necessary, to combine it atomically with the pledge leg) meant nothing ever updated the bank's Postgres ledger — a silent, permanent divergence from on-chain truth, discovered only by checking the bank's `/clients` endpoint after a real settlement and finding it stale.
3. **First velocity-cap limit** (Phase 4, spec-001.md's Example trade): the bank's Transfer Hook caps every client at $5,000,000/hour maximum, with no tier above it — discovered only when a real $10,000,000 transfer was rejected on-chain, not by reading `compliance-hook`'s source ahead of choosing the trade size.
4. **Second velocity-cap limit** (Phase 6, spec-001.md's Example trade): the first fix checked only the open leg's sender (Buyer, low risk, $5,000,000 cap) and missed that the close leg's sender (Seller, medium risk, $2,000,000 cap) faced a different, lower limit — discovered only when a real close transaction was rejected, leaving a permanently-stuck trade (`fixtures/retired-trades.md`) as the cost of not checking sooner.

**The norm:** when reusing an external system unmodified, budget for its real operational constraints — auth model, data ownership, business-rule limits — to surface only during build, not before. Reading its docs or intent.md's own constraints section first is necessary but not sufficient; several of the constraints above were never written down anywhere, only enforced in code. When one such constraint is found, check for siblings before treating it as resolved — a limit found on one party's account or one code path almost certainly applies, differently, to every other party's account or path too. Incident 4 above is the direct cost of skipping that check the first time: the fix for incident 3 checked only the account that had actually failed, not the other party's equivalent constraint, and that gap became its own incident two phases later.
